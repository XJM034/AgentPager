# GLM 钥匙串重复授权修复与签名验证

## 目标与当前交付状态

用户要求授权一次后正常使用不再定期输入密码，GLM 额度仍每十分钟自动更新；不能只隐藏弹窗、实际停止更新却仍显示可用。

用户批准后，已启用固定本机签名并安装 **0.3.0 Build 15**。真实 GLM 查询、重启后的读取和两个正常十分钟自动刷新周期均通过；13:32 至 13:53 的本机 securityd 日志中，新版进程的钥匙串弹窗记录为 0。本轮提交范围为修复代码、测试、打包脚本和文档，不包含本机证书、密钥、签名配置或构建产物，**不执行推送**；不能把隔离测试、真实账号查询和 Redmi 画面验收混为一谈。

## 原因与边界

- 本机 securityd 日志在 10:54、11:04、11:15、11:25 记录了 GLM Key 的授权请求，与协调器 600 秒轮询一致。更新前 Xcode 调试版也有相同现象，因此并非设置页层级调整引入了鉴权逻辑变化。
- 原 `GLMKeychainStore.load()` 每次读取允许系统交互；钥匙串仍记录旧构建的临时签名要求。新构建身份不同，一次性“允许”不能代替稳定、持久的应用授权。
- 修复前本机没有代码签名身份。临时签名的 designated requirement 依赖代码哈希，不能承诺跨版本延续授权。
- 依据：[Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)、[Apple TN2206](https://developer.apple.com/library/archive/technotes/tn2206/_index.html)。本地自签身份不等于 Developer ID 或 Apple 公证。

## 改动

- 将后台读取与主动“授权读取”分离。启动、手机连接、手动刷新、定时轮询都不自动调用授权入口。
- 保留现有文件钥匙串的 service/account，不迁移、不删除真实 Key、不修改已有访问控制列表。
- 先检查条目所属钥匙串是否锁定，再以禁止交互策略读取；共享进程锁保护策略切换，并在成功或失败后恢复原策略。配对的钥匙串调用也使用这把锁，不改变配对服务、密钥、协议或原有授权方式。
- 系统授权后立即复查静默读取；复查失败显示授权未保留，不以一次交互读取成功代替后台可用。成功后立即查询并恢复 600 秒刷新，不长期缓存 Key 绕开锁定或撤权。
- 设置页明确提示钥匙串授权问题，不与 GLM 接口的 401/403 混淆。失败保留可信旧数据及其最后成功时间；手机继续使用现有陈旧/不可用状态，无跨平台契约变更。
- 打包可从本机固定证书指纹文件选择身份，显式 `-` 正确报告为临时签名。不会自动创建证书、写指纹文件、修改系统信任或降级已选身份。
